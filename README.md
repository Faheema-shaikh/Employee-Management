# Employee-Management
A Spring Boot REST API for managing employee records using a layered architecture. The application supports creating, retrieving, updating, and deleting employees, with request validation, DTO-based responses, centralized exception handling, PostgreSQL persistence, and Swagger UI documentation.
Features
- Create, retrieve, update, and delete employee records
- Layered structure: Controller, Service, Repository, Entity, DTO, and Exception Handler
- Request validation using Jakarta Bean Validation
- Request and response DTOs; API responses do not expose JPA entities
- Centralized error responses using @RestControllerAdvice
- Duplicate email checks
- PostgreSQL database integration with Spring Data JPA / Hibernate
- Transaction management in the service layer
- Swagger UI / OpenAPI documentation
Tech Stack
- Java (use the version configured in pom.xml)
- Spring Boot
- Spring Web
- Spring Data JPA / Hibernate
- PostgreSQL
- Jakarta Bean Validation
- Springdoc OpenAPI / Swagger UI
- Maven

Employee fields
The employee request contains the following fields:
- firstName
- lastName
- email
- phoneNumber
- department
- designation
- salary
- status
  The id is generated by the application/database.
  Sample request: Create an employee
  POST /employee
  Content-Type: application/json      
  {  
  "firstName": "Aisha",  
  "lastName": "Khan",  
  "email": "aisha.khan@example.com",      
  "phoneNumber": "9876543210",  
  "department": "Engineering",  
  "designation": "Software Developer",  
  "salary": 60000.0,  
  "status": true  
  }  
  Sample success response
  The API returns an employee response DTO rather than the JPA entity. Example:  
  {  
  "id": 1,  
  "firstName": "Aisha",  
  "lastName": "Khan",  
  "email": "aisha.khan@example.com",  
  "phoneNumber": "9876543210",  
  "department": "Engineering",  
  "designation": "Software Developer",  
  "salary": 60000.0,   
  "status": true  
  }  
  The generated id and returned values depend on the data saved in your database.
  Validation and Error Handling  
  The API validates incoming request data and uses a centralized exception handler to return structured error responses.

Expected error scenarios include:
- 400 Bad Request — invalid request data or JSON
- 404 Not Found — employee ID does not exist
- 409 Conflict — duplicate email or a database integrity conflict
- 500 Internal Server Error — unexpected server-side error
  An error response may look like this (the exact values depend on the error):  
  {  
  "timestamp": "2026-10-23T10:00:00Z",  
  "status": 404,  
  "error": "Not Found",  
  "message": "Employee not found with id: 99",  
  "path": "/employee/99",  
  "validationErrors": {}  
  }   

  For validation failures, validationErrors can contain field-specific messages.
